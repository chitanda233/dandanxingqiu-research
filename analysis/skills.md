# 技能与数值：字段、样本和生效约束

版本 242 中 [主动技能表](../analysis/data/skill_skill.json)有 8,237 行，[被动技能表](../analysis/data/passive_skill_passive_skill.json)有 8,932 行。这些行包括测试、怪物、不同等级、隐藏效果与历史配置，不能说玩家可装备 8,237 种技能。表是从原始 Lua 5.1 字节码执行导出，中文名和说明由 [主动语言表](../analysis/data/language_define_skill.json)、[被动语言表](../analysis/data/language_define_passive_skill.json)关联；脚本与哈希见[导出清单](../analysis/data/manifest.json)。

## 如何读一行技能

常见字段：`id` 是具体等级/变体，`prototype_id` 是机制原型；`effect` 是一组按 `index` 排列的效果；`cost` 给费用种类和值；`init_cd` 初始冷却、`turn_cd` 回合冷却、`turn_max` 每回合次数、`match_max` 单局次数；`pve_*` 是 PVE 覆盖值。未填字段不能当作 0。`-1` 在诸多行表示没有配置限次，仍可能被战斗规则限制。[原表](../analysis/data/skill_skill.json)

客户端 `unit_can_use_skill` 真实检查技能是否在角色持有列表中、当前回合与行动状态、沉默、定身/位移、重复回合、`turn_max`、`match_max`、CD、禁用类型和费用。技能实际效果与资源扣减由服务端回包推进。[校验调用](../reverse/lua-decompiled/game.module.fight.manager.base.fighting.skill.core.lua#L177)

## 武器主动技能：一把武器有多档

例如 `搬砖水泥桶` 系列：`2110011` 基础档双子弹，每颗说明为 17.6%+2，CD 2；`2110021` 真档 19.4%+3；`2110031` 极档 23.2%+3；`2110041` 绝档 25.6%+4；`2110051` 超档 27.6%+条件加成 3.1%+5；`2110061` 神档 30%+条件加成 5.3%+6。效果字段分别含 `100` 比例、`101` 固定项、`8=1`（第二发的索引从 0 起）与 `61.jellyfish_info` 两枚偏角 ±5 的子弹配置。[技能表](../analysis/data/skill_skill.json)

`许愿魔杖` `2126011` 一发信号弹 25.6%+6，再召流星 76.8%+20；真档 `2126021` 为 28.2%+7 / 84.5%+23；极档 `2126031` 为 33.8%+9 / 101.4%+28；绝档 `2126041` 为 37.2%+10 / 111.5%+31。这里的“多段总伤”不能简单相加，因为目标选择、命中、暴击和独立伤害事件要由战斗节点确认。[技能表](../analysis/data/skill_skill.json)

## 被动技能不是一张增伤百分比表

被动表效果形态包括 `ps_add_buff`、`ps_add_energy`、`ps_add_anger`、`ps_check_obj_num` 等。例：ID `2` 的 `ps_add_energy={prob:10000,add_value:50}`，ID `3` 的 `ps_add_anger` 同值；其中 10000 可能是万分比基数，但需通过实际触发器确认。ID `4/5` 的 `ps_check_obj_num` 限定空间宽高、阵营、数量再加分。被动可以改资源、状态、召唤物与触发条件，不是只改攻击乘区。[被动表](../analysis/data/passive_skill_passive_skill.json)

## 数值字段的适用边界

技能 `effect.100` 常与文字中的伤害率×100 相合，如 `2005233` 的 12050 对应 120.5%；`effect.101` 常是固定项。但这仅说明**该技能字段的编码**，不能推出最终伤害公式。技能触发后还会进入伤害、命中、暴击、护盾、目标状态、PVP 平衡和服务器节点链。更完整的输入与轨迹见[局内计算](combat-math.md)。

## 技能养成设计：从未解锁到可上场

### 数据对象与装备空间

局外培养用基础 `skill_id`，局内使用具体 `cf_skill_id`。例如培养索引 1001 与局内冰冻档位 `1001009/1001049` 是两个粒度；等级、原型和确切技能行必须分别存储。装备请求提交 `plan_id/pos/skill_id/opt`，`opt=1` 是装备，其余走卸下；升级请求只提交基础技能 ID，升级结果由回包的新等级替换 `id_to_skill_lv`。

客户端常量列出槽位 `[1,2,3,100,101]`；`get_slot_count` 未缓存时返回 5，`get_active_slot_count=1`，`get_passive_slot_count=2`。这不等于五个普通主动技能槽：100/101 是单独编号，主动与被动有自己的类别约束。计划、当前计划和按玩法选择的计划分别存在，获取技能不自动证明当前战斗携带它。[槽位与等级计数原指令](../reverse/lua-disassembled/game.module.skill.manager.core.txt#L1070)、[装备网络](../reverse/lua-luadec/game.module.skill.manager.network.network.lua)、[槽位常量](../reverse/lua-disassembled/game.module.skill.manager.const.txt)

### 升级按钮按什么顺序判断

`can_upgrade_skill_lvl(id,是否提示缺材料)` 的实际顺序如下；任意一步失败即返回 false，不进入后续费用判断。

| 顺序 | 条件 | 策划规则 |
| --- | --- | --- |
| 1 | 读取当前等级，未持有按 0；查当前等级培养行 | 解锁也使用同一培养路径；缺行不提供升级 |
| 2 | 角色等级 ≥ 当前行 `require_lvl` | 账号门槛独立于技能等级 |
| 3 | 配了 `open_func_id` 时该功能已开放 | 开放状态变化会影响培养资格 |
| 4 | 达到指定等级的技能数量 ≥ `require_skill_lvl[1]` | `[数量,等级阈值]` 是其他技能的横向培养要求；空表按数量0、阈值1 |
| 5 | 配了任务时，任务存在且状态为 finish | 这里只读完成状态，不以进度数字代替 |
| 6 | `open_day − floor(开服天数) ≤ 0` | 开服日与角色级要同时满足 |
| 7 | 下一等级配置存在 | 即使当前行有材料，也不能越过培养上限 |
| 8 | 当前行前两组费用余额足够 | 一组材料加一组货币；无费用/空费用才通过 |

重要修正：**消耗取当前等级行，不取目标等级行。** 1001 在 20→21 时消耗技能知识×4,000、金币×90,000；40→41 时需角色40级、开服第5天、技能知识×7,500、金币×150,000。原始字节码验证了材料少1失败、角色39级失败、开服第4天失败、其余门槛满足后通过。达到20级的累计支出是0–19行之和，40行费用也不是“升到40级总费用”。[升级判定原指令](../reverse/lua-disassembled/game.module.skill.manager.core.txt#L753)、[受控验证输入与结果](../analysis/data/client_rule_probes.json)

`can_upgrade_skill_lvl_no_resource` 保留上述开放、任务、等级与下一行检查，跳过余额检查。因此“满足升级前置”“有足够资源可以升级”是两种状态；一键升级还走独立请求，服务端回 `up_skill_list` 后逐技能写新等级。

## 局内释放设计：资格、资源、次数与冷却

### 普通技能的拒绝顺序

在普通手动调用中，判定从战斗 `attack` 状态开始，再检查持有具体技能、本回合行动者、行动阶段、回合动作禁用、自动战斗、沉默与特定定身/蓄力限制，然后检查重复回合禁冰冻、原型禁用、回合次数、单局次数、CD、禁用类型计数、技能互斥、费用及后续位移限制。魂类技能走独立的目标/次数分支，不能套成所有技能一张按钮规则。[完整原指令](../reverse/lua-disassembled/game.module.fight.manager.base.fighting.skill.core.txt)

原函数会把第4个参数重置为 false；第5个旁路标记只绕过特定状态/阶段检查，不绕过所有限制。费用辅助函数虽有“新技能费用减去旧互斥技能费用”的分支，不能因此声称普通按钮校验会自动退款。

| 输入场景 | 原始字节码返回 | 玩家状态的含义 |
| --- | --- | --- |
| 不在 attack | `false,state` | 当前战斗阶段不接受释放 |
| 不是行动者 | `false,not_round_attacker` | 旁观别人行动时不能手动施法 |
| 已离开行动阶段 | `false,fired` | 发炮后的回合阶段不能再次普通释放 |
| 已开启自动战斗 | `false,auto_battle` | 手动技能入口被占用 |
| 沉默 | `false,silent` | 有费用和 CD 也不能释放 |
| 冰冻处于重复回合 | `false,repeat_ban_freeze` | 防止特定连续回合控制组合 |
| 当前回合/本局次数已满 | `turn max` / `match max` | 两个独立计数器 |
| CD 大于0 | `false,cd` | 费用充足不抵消冷却 |
| 费用1需10000，strength=9999/10000 | false / true | 等于费用边界时允许 |

以上是明确桩输入下执行**原始字节码**的结果，不是在线对局实测。[完整探针证据](../analysis/data/client_rule_probes.json)

### 四种费用以及模式覆盖

费用类型 `1=strength`、`2=energy`、`3=anger`、`4=wakan`；前三者读取单位属性，wakan 从魂属性接口取值。`cost=[1,10000]` 是 strength 资源，不是金币或永久角色属性扣除。重复回合还可选对应费用；单局上限在 `is_dungeon_play()` 为真时读取 `pve_match_max`，否则读 `match_max`。技能行的 `pve_*` 与模式层 `use_skill` 是不同层级：模式不许用技能时，不能靠 PVE 次数大于0解锁按钮。

### 回包如何推进一次释放

`update_skill_cost` 使用回包 `round_count/all_count/use_round` 更新状态：先撤销旧回合次数造成的禁用类型计数，再写入新次数并重新施加禁用；单局计数另存；`cd=max(use_round−unit.round_count,0)`。技能使用图标按新旧回合次数差更新。互斥技能替换会先撤旧效果，再记录新技能。按钮预览、本地选择、服务器确认和效果播放是四个节点。[次数更新与互斥处理](../reverse/lua-disassembled/game.module.fight.manager.base.fighting.skill.core.txt)

单位获得自己的行动回合时，普通技能 `round_count=0`，`cd=max(cd−1,0)`；固定 CD 原型表含2139，它跳过普通递减。CD3的受控案例返回CD2、回合次数0。因此不能按其他角色轮次或秒数推算“冷却3”。

### 构筑实例：同一控制机制的不同档

冰冻 `1001009` 为每回合1次、单局1次、CD4、替代普通攻击；`1001049` 为单局3次、CD3，仍每回合1次，也仍被重复回合禁用。两档 `forbid_list` 同时包含 `[11,12,13,14,23,2,3,24,25]`，必须结合互斥类型计数处理，不能允许所有增攻技能同时叠上冰冻。净化 `1009009→1009049` 则从单局1次/CD4变为3次/CD3，`cancel_normal_atk=0`。同样是升级后“更常用”，是否替代普攻却不同。下方将这些等级档、限制与说明一并展开，方便构筑比较。

## 效果与说明冲突的处理

机制原型、具体等级行、效果节点和语言描述分别保留。治疗特例1006999的说明次数/回血值与效果字段不一致，正文不把文本当权威运算。冰冻则引用 buff1001001；治疗/群疗有效参数、净化的删除类型和数量应沿 effect→buff/节点继续核对。客户端负责可用判断与表现，最终伤害取整、驱散优先级和命中结算仍缺服务器执行器；本页没有伪造该部分公式。
