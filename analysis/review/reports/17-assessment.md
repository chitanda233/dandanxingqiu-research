# 功能评估、复原优先级与缺口

## 本次已经可以交付的功能规格

已有证据足以编写客户端层面的：模式开关矩阵、技能槽与费用、培养资格、弹道三分支、HP更新边界、匹配前检查、剧情星奖/速通、爬塔噩梦系数、材料奖励次数、肉鸽难度/节点、弹球球组/布局/结果、农场操作、公会权限、月卡/广告/通行证状态。

这些章节不仅列模块，还给输入、状态、条件、输出、费用方向与例外。功能目录补全189个命名空间，配置浏览器覆盖1555份成功输出；未深入验证的模块保留“结构索引”，便于后续研究而不夸大完成度。

## 产品结构的主要特点

**操作与构筑共存**：蓄力、角度、风和弹道决定操作，武器、技能、宠物与模式平衡决定构筑。**多套PVE并行**：关卡、塔、材料奖励、肉鸽选择和弹球布局分别提供不同推进对象。**社交进入资源循环**：公会愿望、共享订单、家园帮助、师徒任务与婚姻培养连接关系和成长。**活动与商业化横跨系统**：月卡、抽取、通行证、商店和节日活动投放不同资源。

这些判断来自功能依赖；不等于已测量哪些系统最受欢迎、付费最强或留存最高。

## 按证据可用性安排复原

| 优先级 | 交付内容 | 原因与依赖 |
| --- | --- | --- |
| P0 | 数据加载、有效配置、ID映射、时间层、请求状态、失败处理 | 后续功能共同基础；默认值错会污染数值 |
| P1 | 模式矩阵、技能计划/升级预算、关卡与领奖、农场资格、月卡/通行证 | 客户端原函数已有可验证条件，适合先复原规则 |
| P1 | 弹球关卡查看器与状态逻辑 | 布局完整50关，计分/提交流程清楚；物理桥接另补 |
| P2 | 公会权限、家园方案、好友/师徒/婚姻流程 | 多状态、异步与关系依赖，需要更大数据模型 |
| P2 | 战斗表现、弹体预测、Buff与分批节点 | 客户端结构清楚，但依赖Unity引擎和协议回放 |
| P3 | 最终伤害、碰撞、匹配选择器、掉落概率执行器 | 缺服务端/引擎权威实现，不能靠常见公式补齐 |

优先级是工程建议，不是开发工时估计；没有工作量和团队信息时不编造“几天复刻完整游戏”。

## 数值设计应避免的错误

1. 直接把配置行数当玩法数量，忽略分片和等级变体。
2. 把字段缺省当0，漏掉Lua元表默认继承。
3. 看到百分比常量就除100或10000，未检查调用单位。
4. 将当前级费用计为升到当前级的费用，累计多算一步。
5. 用普通面板换算代替公平模式属性替换。
6. 用推荐战力/软提醒实现硬禁入。
7. 预览候选直接覆盖实例，漏掉确认/取消。
8. 每次重玩都按首通奖励到账，漏掉已领/已完成状态。

## 战斗与玩法设计应避免的错误

技能CD不是秒数；一次发炮不是单节点单伤害；HP直接同步没有统一双边钳制；阻力弹道不是标准闭式抛物线；剧情下一关逻辑被固定开关关闭；弹球布局球数覆盖默认球数；PVE奖励额度不是挑战资格；肉鸽未完成节点不能提前跳下一节点。

这些具体差异有原指令或测试支撑，属于可以立即修正的规格问题。负数边界用例不证明线上漏洞，也不应该写成玩家可执行的作弊流程。

## 下一步真正需要的新证据

| 缺口 | 需要的证据 | 可以回答的问题 |
| --- | --- | --- |
| 最终伤害与碰撞 | 权威执行器或足够完整的可控战斗回放/引擎桥接 | 乘区、盾优先级、取整、实际命中 |
| 匹配与机器人投放 | 选择器、服务端文档或可控样本 | 扩圈、隐藏分、等待阈值 |
| 抽取概率 | 完整池权重与选择器、保底重置链 | 单抽/十连概率与期望 |
| 当前开放状态 | 当前服务器/账号功能列表、云开关与活动回复 | 哪些缓存功能真正在线 |
| 真实经济与体验 | 当前价格、收益、玩法统计与实际UI流程 | 最优投入、效率、留存与体验负担 |

本次已经完成离线缓存所能支撑的复查与详细Web交付；以上缺口不能通过继续堆客户端表格诚实解决。
